# 报表文档规范

**适用范围**：写在语雀 `梦宇-报表自动化` 知识库下的报表文档。这些文档被 WeKnora 同步成
知识库内容，供「报表助手」智能体检索。智能体靠文档里的信息决定**查哪张表、用哪条 SQL、
把用户的自然语言条件换算成什么参数**。

**不在本文档里的东西**：数据库的连接地址与凭证。凭证由平台的沙箱密钥加密存放，见
`skill/order-report/SKILL.md`。**任何情况下不要把 host / 账号 / 密码写进报表文档。**

---

## 一、为什么规则长这样

这份规范里的每条硬规则都对应一个已确认的系统行为。知道原因，遇到边界情况才能自己判断
该怎么写。

| 规则 | 原因 |
| --- | --- |
| 一篇文档 = 一个报表 | 文档切块粒度是 512 token（重叠 80）。多个报表混一篇，相邻 chunk 语义互相污染，检索会命中错的报表 |
| 每个查询场景单独一个 `###` 小节，标题用用户的原话 | 检索是语义 + 关键词混合检索（RRF 融合）。用小节标题承载「用户会怎么问」，等于给检索装了锚点 |
| SQL 模板要短，放 ` ```sql ` 围栏 | 切块器会保护 **Markdown 表格行**的完整性（跨块还会自动重复表头），但**不保护代码块**。模板过长会被拦腰截断，智能体拿到半条 SQL |
| 表结构、口径、输出列都用 Markdown 表格 | 同上：表格是全文里结构最安全、切块后语义最完整的形式 |
| 参数必须给参数名，不能只用自然语言描述 | 智能体要把用户的话映射成 `:参数` 占位符。没有参数名它只能猜，猜错就是错数 |
| 必须声明「本报表不覆盖什么」 | 没有这条，智能体遇到超范围的问题会硬编一条 SQL 出来 |
| 文档必须是语雀「文档」类型、且已发布 | 同步连接器只取 `type == "Doc"`（跳过「表格」「画板」等类型），只取已发布状态（草稿不取），且只取 Markdown 格式的正文 |

## 二、固定章节模板

**八节，顺序固定，标题文字固定。** 智能体的提示词按节号引用（「读文档 §6 参数契约」），
改标题会破坏这个约定。

````markdown

## 1. 报表说明
一段话讲清：这是什么报表、回答什么问题、数据来自哪张表、更新频率与数据延迟。

## 2. 适用问题
用户可能怎么问（原话、口语、别名），5~10 条：
- "上个月张三的达人订单明细"
- "7月1号到15号哪些达人出单了"
- "帮我导一下最近的达人订单"
- "达人订单报表"、"达人出单数据"

**本报表不覆盖**：<列出容易混淆但本文档不管的问题，并指向正确文档>

## 3. 数据来源
- 库：`<库名>`
- 主表：`<表名>`
- 关联表：`<表名>`（关联键：`<字段>`）
- 时间字段：`<字段>`（含义、时区）

## 5. 字段口径与陷阱
- **金额**：单位（元/分）、是否含税、是否含运费
- **去重**：一行代表什么（一个订单？一个订单行？子订单？）
- **退款/取消**：如何处理，哪些状态算有效订单
- **状态枚举**：取值 → 含义对照表
````

## 三、逐节写作要求

### §1 报表说明
三到五句话。必须点明**这张报表的边界**——「基于 X 表的 Y 维度明细」比「订单相关报表」
有用得多。写上更新频率和数据延迟，智能体才能回答「数据到几号了」。

### §2 适用问题（**检索命中的关键**）
这是全篇最重要的一节。写**用户的原话**，包括：
- 口语说法：「帮我导一下」「来个 Excel」「看一下」
- 别名与简写：「达人」也叫「网红」「博主」「KOL」「达人号」
- 时间表达：「上月」「上个月」「最近一个月」「7 月上半月」
- 指标口语：「出单量」「卖了多少」「订单数」

至少要覆盖到用户真实会问的说法。检索是全库混合检索，这一节相当于给这篇文档挂关键词。

**「本报表不覆盖」必须写。** 列出容易混淆的问题并指向正确文档。例如达人订单报表要写明
「结算金额、佣金账单不在本报表，见《达人结算报表》」。没有这一段，智能体遇到结算类问题
会拿订单表的字段硬凑。

### §3 数据来源
- 库名必写（智能体要在回答里说明口径来源）。
- 主表、关联表、关联键必写。
- **时间字段要写清是哪个**——很多表有多列时间（下单时间、支付时间、发货时间、更新时间），
  用错列会导致数字对不上，而表面上看不出错。
- 时区必写。跨时区时边界日的归属会变。
- 更新频率与延迟必写。

### §4 表结构
**每个字段一行**，不要只列常用字段。智能体靠这张表核对 SQL 里的列名，缺字段会导致它
无法验证。

「口径 / 枚举」列写这个字段的业务含义与取值。枚举值必须列全，例如
`order_status`：`paid` 已支付 / `pending` 待支付 / `closed` 已关闭。**只写「订单状态」
等于没写**——智能体不知道 `paid` 和 `pending` 哪个算有效订单。

### §5 字段口径与陷阱（**数字对不对得上的关键**）
这一节决定报表的数字能不能和业务方对上。写具体，别写「按业务规则处理」：

- 金额单位：`pay_amount` 单位是**元**还是**分**？含不含税？含不含运费？
- 去重：一行是一个订单、一个订单行、还是一个子订单？同一个 `order_id` 会不会出现多行？
- 退款：退款订单算不算「成交」？`refund_status` 为 `refunded` 的行要不要排除？
- 状态：哪些状态计入。
- NULL：`influencer_id` 为空代表什么（非达人订单？未绑定？）。
- 脏数据：如果有已知异常（重复推送、测试单），写清用什么条件排除。

**最容易出错的写法**：只描述字段「是什么」，不描述「算什么」。请一律写成可执行的条件，
例如「有效订单 = `order_status = 'paid'` 且 `refund_status != 'refunded'`」。

### §6 参数契约
**参数名必须与 SQL 模板里的 `:占位符` 完全一致。** 命名用 `snake_case`。

「自然语言说法示例」列写用户可能怎么说这个条件；「归一化规则」列写怎么换算，越明确越好：

- 好：`"上月" → 上一个自然月 1 日 00:00:00（含）到本月 1 日 00:00:00（不含），时区 Asia/Shanghai`
- 差：`"上月" → 上个月`

**日期区间的开闭必须写清，而且全文只能有一种口径。** 两件事分开看：

- **SQL 层必须是左闭右开**：`>= 起始` 且 `< 结束的次日/次月`。这样就不会有
  「31 日 23:59:59 之后的数据算不算」的争议。下面两种写法都满足这条，二选一：
  - **含当日**（推荐）：`:end_date` 传用户说的结束日**当天**，SQL 里写
    `< DATE_ADD(:end_date, INTERVAL 1 DAY)` 自己补次日。参数值和用户原话字面对应，
    少一次人工换算就少一次算错的机会。本 fork 的《达人订单报表》用的是这种。
  - **传次日**：`:end_date` 由调用方先换算成结束日的次日，SQL 里直接写 `< :end_date`。
- **选定后在 §6 的「归一化规则」里写死，§7 的模板必须与之一致。** 两处口径不一致会整体
  差一天，而且**执行时不报任何错** —— 这是本类文档最难查的一种错。

**可选参数**（`必填：否`）要额外写清两件事：

1. **不适用时传什么。** 执行脚本**不给任何参数补默认值**，模板里出现的每个 `:占位符`
   都必须在 `--params` 里有键。所以「必填：否」的语义是「用户不必指定」，
   **不是「调用方可以省略这个键」** —— 漏传会直接报 `缺少参数` 并退出。
2. **空值等价于什么。** 建议统一约定为「不限」，并且**同时覆盖 `NULL` 和空串 `''`**：
   守卫写成 `(:param IS NULL OR :param = '' OR <正常条件>)`。只判 `IS NULL` 的话，
   调用方传空串会让条件静默滑向两个相反的极端（字符串相等类返回全量、集合匹配类返回 0 行），
   而两者看起来都像「正常结果」。

必填参数要标必填——智能体在缺必填参数时会**追问用户**，而不会自己假设一个默认值。

### §7 查询模板（**核心**）
每个场景一个 `###` 小节。要求：

1. **小节标题用用户问法**，不要用技术命名。写「### 7.1 查询某达人某时间段的订单明细」
   而不是「### 7.1 order_detail_by_influencer」。
2. **模板保持短**。单个模板控制在约 60 行以内。超长就拆成两个场景，而不是塞成一条巨型
   SQL——切块器不保护代码块，长 SQL 会被截断。
3. **日期一律用占位符**。禁止在模板里写死日期，否则模板不可复用且会给出陈旧数据。
4. **只读**。只写 `SELECT`；不要用 `FOR UPDATE`、不要写多条语句、不要出现
   `INSERT/UPDATE/DELETE/DROP/ALTER/CREATE/TRUNCATE/INTO/OUTFILE` 等关键字（执行脚本会
   直接拒绝，学生产事故）。
5. **用显式 `JOIN`，不要用逗号连接表**。执行脚本的表名白名单只识别 `FROM` / `JOIN`
   之后的表名，`FROM a, b` 里的 `b` 会被漏掉，白名单就形同虚设。
6. **不要加 `LIMIT`**，行数上限由执行脚本统一压制（默认 5 万行）。你在模板里写 `LIMIT`
   反而会限制正常导出。
7. **列名要对齐 §4**。模板里引用的每个列都应该能在 §4 找到。
8. **输出列表要全**。「列名」写 SQL 里的别名，「中文表头」写用户看到的中文列名。智能体
   会把这张表转成执行参数，中文表头直接决定 Excel 里的列名。

### §8 输出文件约定
写清文件名格式与工作表名。文件名里**不要用空格和括号**——智能体在回答里用
`sandbox:<文件名>` 引用文件，空格和括号会让引用产生歧义（执行脚本会自动把这类字符
换成 `_`，但与其依赖清洗不如一开始就写对）。

## 四、写作硬规则（违反会导致失败）

1. **不写凭证**。host、端口、账号、密码一律不出现。
2. **不写死日期**。模板里一律用 `:参数`。
3. **不用 HTML `<table>`**。用 Markdown 表格。
4. **不放图片**。报表文档不需要图片，图片会挤占切块预算。
5. **一篇文档只讲一个报表**。
6. **参数名、列名、表名全篇一致**。§4 写的列名、§6 的参数名、§7 的模板，三者必须能对上。
7. **不写「见某某群/问某某人」**。知识库文档要自包含。

## 五、反例

| 反例 | 后果 |
| --- | --- |
| 一篇文档塞 5 个报表 | chunk 语义混淆，检索命中错报表，智能体拿错表查数 |
| 300 行 SQL 不分节 | 被 cut 在中间，智能体拿到半条 SQL，报语法错 |
| 只写「按业务规则过滤退款」 | 智能体无法执行，只能自己编一个条件，数字对不上 |
| 枚举只写「订单状态」不列取值 | 智能体不知道 `paid`/`pending` 哪个算成交，把待支付也算进销售额 |
| 参数只用文字描述、不给参数名 | 智能体无法稳定填空，同类问题每次结果可能不同 |
| 时间字段写法模糊（表里有 4 个时间列却只说「时间」） | 用错列，数字偏差但表面看不出错 |
| 模板里写死 `2026-08-01` | 三个月后还在返回 8 月的数据 |
| 把连接串写进文档 | 凭证进向量库，任何能检索该库的用户都可能问出密码（而且智能体根本不用它） |
| 用语雀「表格」/「画板」类型写 | 连接器只取「文档」类型，永远同步不进来 |
| 写成草稿不发布 | 连接器只取已发布状态，不同步 |
| 用 `FROM a, b` 逗号连接 | 白名单漏检 `b`，安全护栏失效 |
| 列名与 §4 对不上 | 智能体核对不出问题，查询报 `Unknown column` |

## 六、发布到语雀的操作约束

1. 在 `梦宇-报表自动化` 知识库下**新建「文档」**（不是「表格」「画板」「多维表格」）。
2. 文档标题 = 报表名称（智能体按标题定位，也是检索权重最高的一段文本）。
3. 建议在知识库里按主题建目录分组（连接器支持保持语雀目录结构），但**不要**把一篇文档
   拆成多篇。
4. 写完**记得发布**。草稿不会被同步。
5. 修改后同步即可更新（连接器按 `content_updated_at` 做增量，会自动重建这篇文档）。
6. 同步是**单向**的：WeKnora 只从语雀拉取，不会写回。文档以语雀为准。
